# 06 · Decision log

Add a row whenever you make a non-obvious choice. To reverse a decision, add a new row rather than editing the old one.

| # | Date | Decision | Why | Revisit when |
| --- | --- | --- | --- | --- |
| D1 | 2026-10-27 | **Monorepo:** `app/`, `api/` and `docs/` in one git repo, with **no** npm workspaces yet | One place for docs and the contract, with history preserved. Workspaces add Metro and tooling friction we don't need while there's no shared code. | We want shared TS types or a shared planner package between app and API. |
| D2 | 2026-10-27 | **Expo Router** instead of using React Navigation directly | It's built on React Navigation, gives file-based and typed routes (already enabled in `app.json`), and is the project rule in `app/AGENTS.md`. | — |
| D3 | 2026-10-27 | **`react-native-maps`** with `PROVIDER_GOOGLE`, not `expo-maps` | In SDK 57, `expo-maps` is **alpha** (with frequent breaking changes) and doesn't run in Expo Go. `react-native-maps` is stable, runs in Expo Go, and supports polylines, draggable markers and `onLongPress`. | `expo-maps` becomes stable. |
| D4 | 2026-10-27 | Google Maps for **rendering only**. Transit data is ours; we use **no Google Directions or Transit API**. | Their transit coverage of informal Pakistani routes is weak, they cost money per request, and their ToS forbid storing results. | — |
| D5 | 2026-10-27 | **No street-address geocoder** in Phase 1. Search covers our own stops and landmarks only. | Users navigate by landmarks. Nominatim's coverage in Pakistan is weak and its usage policy forbids heavy app traffic, and Google Places costs money. It also works offline. | Users keep searching for things we don't have. Then consider Places Autocomplete as a fallback. |
| D6 | 2026-10-27 | **TanStack Query + `fetch`** instead of axios | Query gives caching, retries and loading/error states for free, and `fetch` is enough underneath. *Keeping axios is fine if you prefer it: it's a swap inside `http-api.ts` only.* | — |
| D7 | 2026-10-27 | **Zustand** for planner state (from, to, chosen option) | It's tiny, needs no providers, and is easy to read from any screen. | — |
| D8 | 2026-10-27 | **In-app mock API** (`MockRaahiApi`) running a real JS planner over fixture data | It works offline, it's deterministic, it can force error states, and the planner becomes the prototype for the backend. A Postman mock server only replays canned responses. | Phase 2: use Postman for API contract tests. |
| D9 | 2026-10-27 | **At most 1 transfer** in Phase 1 | It covers most real trips. Each extra transfer grows the search space a lot and makes trips harder to explain to users. | Real data shows common trips needing 2 changes. |
| D10 | 2026-10-27 | **GTFS-shaped data model** with one **variant per direction** | We can import real GTFS if any turns up. Modelling direction explicitly prevents "right bus, wrong way" results. | — |
| D11 | 2026-10-27 | **AsyncStorage** for preferences and saved trips; SQLite deferred | The data is small key-value JSON. SQLite only earns its keep for whole-network offline mode. | Phase 3 offline network. |
| D12 | 2026-10-27 | **Android-first**, with an **EAS development build** from M0 | It's the target platform. RTL is disabled in Expo Go, and release maps need the API key. | — |
| D13 | 2026-10-27 | The Google Maps API key comes from an env var through `app.config.ts`, and is **never committed** | Keys committed to a public repo get abused and billed. | — |
| D14 | 2026-10-27 | **Launch city: Karachi** | It's the team's city, so routes can be ridden and verified first-hand, and we already have route text data. | — |
| D15 | 2026-10-27 | **Informal minibus/coach routes are the primary target**; government services (People's Bus, BRT) are an add-on | That's what everyday Karachi commuters actually ride. | Informal data can't be kept accurate enough. |
| D16 | 2026-10-27 | **Identify buses by route name only.** No colour, plate, destination board or fare. Direction is shown as "towards ‹last stop›". | Many vehicles share one route name and have no consistent markings; fares are out of scope. Keeping per-direction variants (D10) still prevents wrong-way trips. | — |
| D17 | 2026-10-27 | Phase 1 stops = **well-known points listed in the route text**, shared through one gazetteer | Buses are hail-and-ride, but route descriptions list landmarks, and shared gazetteer IDs are what make transfers work. | Phase 2+: board or alight at the nearest point on a route's shape. |
| D18 | 2026-10-27 | Fares and women-specific features are **out of scope** | Product decision. | — |
| D19 | 2026-10-28 | **Stay on Google Maps** (D3, D4), locked down so it can't bill: enable **only** Maps SDK for Android, restrict the key to that API and to the app's package name + SHA-1. Walking legs are straight lines, plus an **"Open walking directions"** button that opens a free [Maps URL](https://developers.google.com/maps/documentation/urls/get-started) in the Google Maps app (no key). | Mobile map loads are free, so with no other APIs enabled there is nothing to bill. Routes/Directions, Places and Geocoding are billed per request, and our own data and search replace them. A budget alert only notifies, so API restrictions are what actually stop charges. | Google starts charging for mobile map loads, or a card can't be kept on the billing account. Then switch to MapLibre (`@maplibre/maplibre-react-native`) with OpenFreeMap or self-hosted Protomaps tiles. Phase 2: walking paths from our own OSRM/GraphHopper (foot profile). |
| D20 | 2026-10-28 | **Optional accounts, local-first.** Reverses "Accounts, login" being out of scope. Every feature, including saved routes, trips and home, works as a guest on the device. Signing in only adds **backup and sync** of saved items. | The assignment needs secure storage and auth. Our users have patchy data and shared phones, so a login wall in front of offline features would block the people who need them most. | Users ask for features that genuinely need an account (e.g. reports tied to a person). |
| D21 | 2026-10-28 | Phase 1 auth is **mocked in `MockRaahiApi`** (fake tokens, in-memory users) against the contract's `/auth/*` and `/me/*` endpoints. Real auth is built in our own Express API in Phase 2. No Firebase/Supabase. | Same swap pattern as D8. A hosted auth provider would be a second backend we'd later migrate users off. | — |
| D22 | 2026-10-28 | **`expo-secure-store`** for secrets and sensitive personal data: auth tokens and saved home/work locations. Everything else (bookmarks, saved trips, prefs) stays in AsyncStorage (amends D11). | It's encrypted with the Android Keystore. Home location is sensitive on shared phones. SecureStore is meant for small values, and route/trip JSON isn't secret. | — |
| D23 | 2026-10-28 | **Route lookup and stop lookup are Phase 1 features.** `/places/search` also returns matching routes, and a new `GET /stops/:id` lists the routes through a stop. | Users already know buses by name ("does D7 go there?") and stops by name ("what passes Nagan?"). One search box for both keeps the UI simple. | — |
| D24 | 2026-10-28 | **Saved items move out of "stretch"**: bookmarked routes and trips stored in full for offline use, plus Home/Work. Sync is a whole-document replace, last write wins. | They're what the optional account syncs (D20). The data is tiny, so a merge protocol isn't worth it. | Users regularly edit saved items on two devices at once. |
| D25 | 2026-10-28 | Phase 1 runs on a **sample fixture** (`data/karachi/sample/build-sample-network.mjs` → `app/src/services/api/mock/fixtures/network.json`): 5 routes using real Karachi codes and place names (W18, D7, G7, Masood, Sheraz), 10 variants, 45 stops, 15 landmarks, with hand-approximated coordinates, illustrative stop orders and straight-line shapes. Every variant is `source: "sample"`, and the About screen says so. | The route text data isn't in `data/karachi/raw/` yet, and the screens and planner needed realistically shaped data now. The format is the real one, so swapping in pipeline output changes no code. | The real Karachi text data lands. Replace the fixture, then delete the generator. |
| D26 | 2026-10-28 | **Noto Nastaliq Urdu** (`@expo-google-fonts/noto-nastaliq-urdu`) for Urdu text, line height 2× font size, applied by the shared `Text` component. Route codes (`latin` prop) keep the system font. | Nastaliq is what Urdu readers expect. The 2× line height avoids clipping. | The M6 side-by-side check against Noto Naskh Arabic on a cheap screen favours Naskh. It's a one-line change in `constants/theme.ts`. |
| D27 | 2026-10-28 | Stop markers on the Plan map come from `GET /stops/nearest` with `radiusM` set to the visible region, rather than a new "stops in bbox" endpoint. | It keeps the contract unchanged and the payload bounded (limit 60, only when zoomed in). | The map needs more than ~60 stops in view, or the API adds a bbox query. |
| D28 | 2026-10-28 | Mock accounts and their saved data live **in memory only**, so they reset when the app restarts. After a restart the stored tokens fail `/me`, the refresh fails too, and the app signs out quietly, keeping all local data. | That's D21 as written. Persisting a fake server to AsyncStorage would put tokens and home there, which is exactly what D22 forbids and what the M1b demo checks for. | Phase 2: the real API. |
| D29 | 2026-10-28 | Icons: Material Icons via `@expo/vector-icons`. Directional icons (arrows, chevrons, walking) are mirrored in RTL by the shared `Icon` component. Tabs use `NativeTabs` `md`/`sf` symbols. | Material is the Android-native look, it's already in the Expo ecosystem, and one wrapper keeps RTL mirroring in a single place. | — |
| D30 | 2026-10-28 | The language switch persists the choice, calls `I18nManager.allowRTL/forceRTL`, then reloads with `Updates.reloadAsync()` (falling back to `DevSettings.reload()` in debug). At boot the app re-checks direction against the saved language, with a one-shot guard (`prefs.rtlPending`) so it can never reload in a loop. Expo Go skips the RTL flip. | RTL needs a native reload. Expo Go resets RTL on launch, so without the guard and the skip it would loop or do nothing. | — |
